# llaisys-26s 任务处理工作流

当用户上传任务截图（图片）时，按照以下两阶段工作流处理。

## 阶段一：生成实现计划（先不执行）

1. **阅读并理解任务截图**：从图片中提取任务编号、函数签名、功能描述。
2. **研究代码库**：
   - 阅读相关源文件，理解现有代码结构和模式。
   - 找到需要修改的具体位置（通常是 `TO_BE_IMPLEMENTED()` 占位符）。
   - 查找代码库中已有的类似实现作为参考模式。
3. **生成计划文件**：在 `plans/` 文件夹下创建 `task<编号>.md`，内容结构如下：

```markdown
# 任务 <编号> — `<函数签名>`

## 任务本质

用简明的语言阐述：这个任务本质上是要做什么？为什么需要这个功能？它在整个系统中扮演什么角色？
（不要照抄任务描述，要用自己的理解重新解释，让读者快速抓住核心）

## 目标

<任务的具体目标描述>

## 背景分析

### 涉及文件
<列出所有相关文件及其作用>

### 关键 API
<列出实现中需要用到的关键 API 及其签名>

### 参考模式
<展示代码库中已有的类似实现模式>

## 实现计划

### 修改位置
- 文件：<路径>
- 行：<行号范围>

### 实现代码
<完整的实现代码>

### 逻辑拆解
<逐步解释每行代码的作用和原因>

## 验证方式
<如何验证实现的正确性>
```

4. **停下等待用户确认**：明确告诉用户「计划已生成，请查看后确认是否执行」。**不要自动执行代码修改。**

## 阶段二：执行计划并记录变更

用户确认后：

1. **执行代码修改**：按照计划修改源文件。
2. **生成结果记录**：在 `Result/` 文件夹下创建 `res<编号>.md`，内容结构如下：

```markdown
# 结果记录 <编号> — `<函数签名>`

## 修改文件

`<文件路径>` — 第 <行号> 行

## 代码变化

### 修改前

（完整展示修改前的代码块）

### 修改后

（完整展示修改后的代码块）

### Diff

（以 diff 格式展示变化，用 +/- 标注增删行）

## 逐行解释

（用表格逐行解释修改后的每一行代码：做了什么、为什么这样做）

## 设计模式参考

（如果参考了代码库中的其他实现，在此展示对照）
```

## 重要规则

- **任务编号**：从图片中提取（如 1.1、1.2、2.1 等），计划文件命名为 `task<编号>.md`，结果文件命名为 `res<编号>.md`。
- **不要跳过阶段一**：即使任务看起来很简单，也必须先生成计划并等待确认。
- **计划必须包含"任务本质"部分**：这是计划文件的第一个实质性章节，放在目标之前。
- **结果文件必须展示前后对比**：包含修改前代码、修改后代码、diff 三种视图。
- **所有文件路径**：
  - 计划文件：`d:\LLAISYS\code\llaisys-26s\plans\task<编号>.md`
  - 结果文件：`d:\LLAISYS\code\llaisys-26s\Result\res<编号>.md`
